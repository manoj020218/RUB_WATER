  Part 2 — Issues That Break 5-Year Operation

  CRITICAL — No Hardware Watchdog

  esp_task_wdt is never initialized. If the firmware hangs (WiFi driver deadlock, Arduino WebServer stuck on a partial
  HTTP client, heap exhaustion), the device is permanently frozen until someone power-cycles it. In an unmanned flood
  installation, that could be weeks.

  Fix — add to setup() in main.cpp:
  #include "esp_task_wdt.h"
  // 30-second watchdog; feeds in loop()
  esp_task_wdt_init(30, true);
  esp_task_wdt_add(NULL);
  Add to loop() at the top:
  esp_task_wdt_reset();

  ---
  CRITICAL — Session Token Expires Incorrectly at 49-Day millis() Rollover

  g_token_expires = millis() + SESSION_TIMEOUT_MS — if this addition overflows (millis near UINT32_MAX), g_token_expires
  becomes a small number. On the next loop, millis() > g_token_expires is immediately true and the session is instantly
  invalidated. A technician connecting at the 49-day mark gets logged out repeatedly and cannot configure the device.
  Multiplied over a fleet over 5 years, this will happen.

  Fix — http_server.cpp session_valid():
  // Replace: if (millis() > g_token_expires)
  // With: unsigned subtraction is safe
  if ((millis() - g_token_expires) < 0x80000000UL == false) { /* expired */ }
  // Simpler — store expire as a duration, check elapsed:
  Simplest correct fix: store the creation time and check (millis() - g_token_created_ms) >= SESSION_TIMEOUT_MS. That's
  the same overflow-safe pattern used everywhere else in the code.

  ---
  SERIOUS — No Factory Reset

  If the default password is forgotten, or if NVS gets corrupted, the device must be reflashed. There is no "hold BOOT
  for 10 seconds to wipe NVS" path. For a device installed in a remote sump or rooftop, reflashing requires physical
  access and a programmer.

  Fix — in setup() after the boot_held check:
  // Count consecutive seconds BOOT is held
  if (digitalRead(9) == LOW) {
      uint32_t hold_start = millis();
      while (digitalRead(9) == LOW && (millis() - hold_start) < 10000) delay(100);
      if (millis() - hold_start >= 10000) {
          nvs_flash_erase(); // or prefs.clear()
          ESP.restart();
      }
  }

  Part 3 — Security Gaps

  Hardcoded password, no change mechanism — HIGH

  DEFAULT_PASSWORD "Hanuman#2026" is the only auth credential. It is the same on every device ever shipped. It cannot be
  changed without a firmware update. The DeviceConfig struct has no password[] field and storage_load/save never
  touches one.

  Every device in your fleet shares one password. If one device is physically captured and the flash is read, the
  password for the entire fleet is compromised.

  Fix: Add char password[32] to DeviceConfig, load/save it in storage.cpp, compare against it in handle_post_login, and
  add a /api/change-password endpoint in the config UI.

  Password sent in HTTP POST over open WiFi — MEDIUM

  The AP has no WPA2 passphrase. The login POST sends the password in plaintext. Anyone within WiFi range can run a
  packet capture and see password=Hanuman%232026 in the HTTP body.

  For a local device in a mechanical room this is tolerable, but for a site with other people nearby it is not. The
  minimal fix is WPA2 on the AP:
  // softAP with a fixed WPA2 key
  WiFi.softAP(g_cfg->device_name, "YourAPKey", AP_CHANNEL, hidden, AP_MAX_CONNECTIONS);
  Ideally the key is derived from the device MAC so each unit has a unique AP password.

  OTA firmware is unsigned — LOW (current scope)

  Any authenticated user can push arbitrary firmware. There is no signature verification. This is acceptable for
  local-only devices but means a stolen password = arbitrary code execution on the hardware.

  ---
  Part 4 — Code Quality & Stability Gaps

  Heap fragmentation from String JSON builder — MEDIUM

  handle_api_status() builds a JSON string with 20+ += concatenations on an Arduino String. Each concat may reallocate.
  On a constrained ESP32-C3, long-running heap fragmentation degrades available memory. After months of continuous
  polling every 2 seconds, this can cause allocation failures.

  Fix — use snprintf into a stack buffer:
  char j[512];
  snprintf(j, sizeof(j),
      "{\"device_name\":\"%s\",\"raw_distance_mm\":%u,...}",
      g_cfg->device_name, g_state->raw_distance_mm, ...);
  send_json(200, j);

  Fragile homebrew JSON parser — LOW

  parseField() in handle_api_config finds a key by substring search then calls toInt() on whatever follows the :. It can
  misparse if a key is a suffix of another (e.g., hypothetical "mm" would match inside "level1_threshold_mm"). It also
  fails silently on malformed input (returns -1, which is caught, but misparse of a valid field returns 0, rejected as
  <= 0). Sufficient for current fields but fragile.

  No firmware config migration — MEDIUM

  config_version is incremented on every save (not on every firmware update). There is no code path that says "if stored
  config_version == 1 and firmware needs version 2, migrate." When a future firmware adds a new DeviceConfig field, it
  will silently load the default value for that field from storage_reset_defaults — that part is fine. But if a field is
  removed or renamed, the old NVS key persists as garbage. Not a blocker today, but will become one on the next
  DeviceConfig change.

  No boot/fault diagnostics in NVS — LOW

  There is no boot counter, no crash reason log, no relay activation log in NVS. After 5 years, diagnosing why a device
  misbehaved is impossible without serial logs.

  sensor_update() always logs on junk bytes — LOW

  Serial.printf("[sensor] skip byte 0x%02X\n", junk);
  Every garbage UART byte (noise, startup glitch) prints to serial. On a production device where serial isn't monitored,
  this wastes CPU time on string formatting. Should be removed or guarded with a debug flag.

  uptime_s counter resets at 49.7 days — COSMETIC

  g_state.uptime_s = millis() / 1000UL — millis wraps to 0 every 49.7 days, so the displayed uptime resets. The device
  keeps working, but the uptime display lies. Fix: track uptime in a uint64_t or add a NVS reboot counter.

  Summary

  The firmware is well-structured, the relay logic is safe, the power management is thoughtful. It will likely run for
  years without touching it. The three things that can stop it cold in the field are: no watchdog (firmware hang =
  permanent freeze), no factory reset (config corruption = unreachable device), and session expiry bug at 49-day millis
  rollover (technician locked out of config UI). All three are 1–2 hour fixes. The security gaps (shared password,
  plaintext over open WiFi) are real but acceptable for a local-AP device in a controlled installation — just not for a
  fleet product.
